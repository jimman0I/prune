# BleachBit-Parity Cleaning Engine — Phase D: Per-App Bespoke SQL

## Context

Phases A/B/C (merged) built generic action types (`sqlite.vacuum`, `winreg`, `json`, `cookie`) that apply the same logic regardless of which app a rule targets. Phase D is different: BleachBit's real corpus has 7 commands (`chrome.history`, `chrome.favicons`, `chrome.autofill`, `chrome.keywords`, `chrome.databases_db`, `mozilla.url.history`, `mozilla.favicons`) that are each a bespoke, hand-written function in BleachBit's own `bleachbit/Special.py` — no shared mechanism, no `address`-style generic parameter. Each deletes specific rows from specific tables in a specific browser's specific database, while preserving bookmarks/saved data that shouldn't be touched.

## Grounding: real current schemas, not BleachBit's documented version branches

`Special.py`'s functions branch on Chrome "history version" numbers documented up to version 42 (Chrome 79, ~2023) and describe Firefox tables that have been stable for over a decade. Real current data on this machine was checked directly (read-only copies, never the live files) before designing anything:

- **Chrome/Brave `History`** (real version on this machine: **70**, far past BleachBit's documented 42): `urls`, `visits`, `keyword_search_terms` (now has both `term` AND a newer `normalized_term` column BleachBit's old code never mentions), `downloads` (still has `current_path`/`target_path`, confirming BleachBit's `ver>=28` branch is the right one -- the older `full_path`/`url` branch is dead), `segments`, `segment_usage` all present and column-compatible with BleachBit's `ver>=28` branch. **The `favicons`/`favicon_bitmaps`/`icon_mapping` tables BleachBit's `chrome.favicons` targets do not exist in this file at all** -- Chrome moved favicon storage out of `History` entirely in a later redesign.
- **Chrome/Brave `Web Data`** (real version: **153**): `autofill` (`name`/`value`/`value_lower`/`date_created`/`date_last_used`/`count`, exactly matching BleachBit's targeted columns) and `keywords` (all of BleachBit's targeted columns present) both real and current. **`autofill_profile_names`/`autofill_profile_emails`/`autofill_profile_phones`/`autofill_profiles`/`local_addresses`/`local_addresses_type_tokens`/`server_addresses` -- the tables BleachBit's `chrome.autofill` also targets for saved-profile data -- do not exist under those names anymore.** Chrome's real current schema stores that under `addresses` and related tables instead, a structurally different, materially riskier feature (deleting someone's actual saved shipping address is a different consequence than clearing form-fill suggestion history) that was never part of this phase's own scope decision and isn't added here either.
- **`Databases.db`** (Web SQL storage, `chrome.databases_db`'s whole target): **confirmed absent** on this machine -- Chrome removed Web SQL support outright. This isn't a file that happens to be empty; the feature itself no longer exists in any currently-supported Chrome/Chromium build.
- **Firefox `places.sqlite`**: no Firefox installation exists on this machine, so `mozilla.url.history`/`mozilla.favicons` could not be independently re-verified against a live current schema the way the Chrome-side ones were. BleachBit's documented `moz_places`/`moz_bookmarks`/`moz_historyvisits`/`moz_annos`/`moz_origins`/`moz_meta`/`moz_inputhistory`/`moz_hosts` schema is ported as-is, with the same honest "not independently verified on this machine" caveat this project has already used elsewhere (the 150%-DPI fix, the elevation-gated registry tests) rather than a false claim of full verification.

**Decision: build against the CURRENT schema only, existence-checked per table/column, no version-number branching.** BleachBit's own approach hardcodes Chrome version thresholds (`ver>=28`, `ver<49`, etc.) discovered over 15 years of releases. A fresh 2026 build has no reason to carry that history -- it checks whether a table/column exists (the same `sqlite_table_exists`-style pattern `cookie.js` already established in Phase C) and acts accordingly, which is MORE robust to a future schema change than a hardcoded version number would be, not less faithful to BleachBit's intent.

**Decision: `chrome.favicons` and `chrome.databases_db` are explicitly excluded from this phase**, not deferred for convenience -- their real targets don't exist in any Chrome version this app will ever run against. Building them would mean shipping code with no file it could ever find.

**Decision: `chrome.autofill` is scoped to the `autofill` table only**, excluding the profile/address-related tables BleachBit's version also touches -- those tables don't exist under BleachBit's names in the current schema, and the real current equivalent (`addresses` et al.) is a different, riskier feature (deleting saved addresses/payment data, not clearing autocomplete suggestions) that deserves its own explicit future decision, not silent inclusion under an "autofill" label.

**Decision: no shred/secure-delete column-wiping.** Same as Phases B/C -- `__shred_sqlite_char_columns`'s randomblob/zeroblob overwrite branch is gated on BleachBit's own `shred` option, which Prune doesn't have. Every port here is a plain `DELETE`, structurally simpler than BleachBit's own function but doing the same real thing (removing the row), matching the exact simplification already applied to `json`/`cookie`.

## What's being built (5 real action types)

1. **`chrome.history`** -- clears browsing history (`urls`/`visits`/`keyword_search_terms`/`downloads`/`segments`/`segment_usage`) while preserving bookmarked URLs. Bookmark preservation reads the browser's own `Bookmarks` JSON file (same directory as `History`) and keeps any `urls` row whose URL is bookmarked; `visits` and the rest are cleared unconditionally, matching BleachBit's own real behavior (a bookmarked site's VISIT COUNT/history entries still clear -- only the bookmark's own URL row in `urls` survives, so the bookmark keeps working).
2. **`chrome.autofill`** -- clears the `autofill` table (form-field value history) only.
3. **`chrome.keywords`** -- clears user-added search engine entries from `keywords` (`where not date_created = 0`, matching BleachBit's own predicate for "not a browser-shipped default"), resets `usage_count` to 0, and does the same to `keywords_backup` if that table happens to exist (existence-checked, not assumed).
4. **`mozilla.url.history`** -- Firefox/Firefox-family equivalent of `chrome.history`: clears `moz_places`/`moz_historyvisits`/`moz_annos`/`moz_origins`/`moz_inputhistory`/`moz_hosts` while preserving bookmarked places, each table existence-checked before being touched (some are legitimately absent on newer Firefox, per BleachBit's own comments).
5. **`mozilla.favicons`** -- clears unbookmarked favicon entries from a Firefox `favicons.sqlite`-equivalent database, cross-referencing bookmark URLs from a sibling `places.sqlite` (read-only `ATTACH DATABASE`, never written to -- only the favicons file itself is quarantined and mutated).

**Mechanism:** each is a small module under `backend/src/lib/cleanerActions/`, following the exact `scan(action)`/`execute(action, ruleName, guards)` shape every prior action type uses, wired into `cleanerRules.js`'s dispatcher under its own real BleachBit command-name string (`chrome.history`, etc. -- matching BleachBit's own vocabulary exactly, in case a future `cleaners.json` rule wants to use the identical name BleachBit itself uses). Each reuses `quarantineFileEdit()`'s `editFn` mode (Phase C) to quarantine the original file before running its own DELETE statements in place via the bundled `sqlite3.exe`, and the same `autoQuarantine`/`excludeFolders`/`excludeExtensions`/`skipRecentHours` guard conventions every prior action type already has.

## Explicitly out of scope

- `chrome.favicons`, `chrome.databases_db` -- confirmed inapplicable to any current Chrome/Chromium build (see above).
- The Chrome `addresses`/payment-related tables (the real successor to BleachBit's old profile-autofill tables) -- a different, riskier feature than "clear autofill," deserving its own future decision.
- New `cleaners.json` rules using any of these 5 action types -- same "engine capability, not content" boundary every prior phase has drawn.
- Safari (Mac-only, irrelevant).

## Testing

Same convention as every prior phase: real temp SQLite files built with the actual current schema (verified against real column names above, not guessed), a real bookmark-preservation case proven end to end (a bookmarked URL survives, a non-bookmarked one doesn't), a real quarantine-then-restore round trip for at least one of the five (the mechanism itself was already proven in Phase C; this phase's own tests focus on each cleaner's specific table logic). `mozilla.favicons`'s cross-file `ATTACH` is tested against two real temp files (a places.sqlite stand-in and a favicons stand-in), confirming the attached database is never itself mutated.
