# Authoring Real cleaners.json Rules for the New Engine Types

## Context

Phases A-D (all merged) built 9 new cleaning-engine action types. Zero real rules in `cleaners.json` use any of them yet -- every one of its 74 rules still uses the original flat `paths` shape (an implicit `delete` action). This is the first real content pass.

## The gap found while grounding this

Every bespoke single-file action type built in Phases B-D (`json`, `cookie`, `chrome.autofill`, `chrome.keywords`, `chrome.history`, `mozilla.url.history`, `mozilla.favicons`) takes exactly one `path` string, expanded via `expandPath()` -- plain environment-variable substitution, **no glob/wildcard support**. The existing rules this pass wants to upgrade (`chrome_history`, `chrome_cookies`, `brave_history`, etc.) use a literal `*` in their paths (`...\User Data\*\History`) specifically to match EVERY Chrome profile folder on a machine (`Default`, `Profile 1`, `Profile 2`, ...) -- `delete.js`'s own `resolveGlob()`/`pathToSegments()` already handle this for the `delete` action type. Converting these rules to the new bespoke types as-is, with the `*` copied over unchanged, would silently stop cleaning every profile except (by accident, if at all) whichever literal string happened to match -- a real regression for anyone using more than one Chrome/Brave/Edge profile, which is common.

**Fix: extend `cleanerRules.js`'s dispatcher itself** (not each action module) to resolve a `*`-bearing `action.path` into every real matching concrete path via the SAME `resolveGlob`/`pathToSegments` functions `delete.js` already exports, then call the bespoke action's `scan`/`execute` once per resolved path, merging results across all of them (summed `sizeBytes`/`freedBytes`, concatenated `skipped`, ORed `present`). This is a small, contained dispatcher-level change, not new logic duplicated across 7 action modules. A path with no `*` resolves to exactly itself (already `resolveGlob`'s documented behavior for the non-wildcard case), so every EXISTING single-path rule from Phases B-D's own tests is completely unaffected.

**Known, accepted limitation carried over from this fix:** if a rule's glob matches N real profiles, N separate quarantine batches get created (one per profile's database, since each bespoke action is inherently single-database and can't merge N separate SQLite files into one `delete`-style batch the way flat files can). `executeRule`'s own `quarantineBatch` summary field can only reference one string, so only the LAST batch created ends up referenced there -- every batch is still fully real, complete, and independently restorable via the Quarantine screen (which lists the whole quarantine root directory, not a single rule's own remembered reference), so nothing is lost or hidden from Quarantine, just not all individually named back from this one execute() call's own summary. This is the same category of already-accepted simplification the existing `delete`/`winreg` merge patterns carry elsewhere in this engine.

## What's being authored

**Upgraded (converted from plain `delete` to the new engine types), across Chrome/Brave/Edge (all 3 already have identical-shaped rules):**
- `{chrome,brave,edge}_history`: gains a `chrome.history` action (bookmark-preserving) for the `History` file, keeping a `delete` action for `History-journal`/`Top Sites`/`Top Sites-journal`/`Visited Links` (files the bespoke action doesn't touch and a whole-file delete is still perfectly correct for -- they're not part of BleachBit's own `chrome.history` function either).
- `{chrome,brave,edge}_cookies`: gains a `cookie` action (default empty keep list = identical whole-file-delete behavior as today, unlocking future keep-list capability) for both real cookie file locations (`Cookies` and `Network\Cookies`), keeping a `delete` action for the two `-journal` sidecars.

**New rules added, same 3 browsers, `recommended: false` (matching this project's existing convention for anything that touches saved user data):**
- `{chrome,brave,edge}_keywords`: a genuinely new capability -- "Search engines you've added," using `chrome.keywords`. Not risky/`is_safe: true` -- losing a custom search engine shortcut is a trivial, easily-redone inconvenience, not the "loses data" category the existing risky-rule badge exists for (unlike history/cookies/saved-cards, nothing personal or hard-to-recreate is lost).
- `{chrome,brave,edge}_autofill_suggestions`: a NEW, narrower rule alongside the existing `_form_history` rule (not a replacement) -- clears ONLY the raw form-fill suggestion table via `chrome.autofill`, explicitly not saved cards/addresses/IBANs the existing whole-file-delete `_form_history` rule already (and continues to) wipe. `risky: true` still applies (it's still personal typed data, even if less sensitive than a saved card), `is_safe: false`.

**Explicitly out of scope for this pass:** Firefox/`mozilla.*` rules (no existing Firefox rule family in `cleaners.json` to build on -- a bigger, separate addition of a whole new browser family, not an upgrade to something that already exists). `chrome_form_history`/`chrome_favicons` are left completely unchanged (the former still wipes the whole Web Data file including cards/addresses, matching its own honest description; the latter has no bespoke engine equivalent at all, confirmed dead in Phase D).

## Testing

A real, load-bearing test proving the glob-resolution fix works: a fixture with TWO real profile folders (`Default` and `Profile 1`), each with its own real cookie/history database, confirming a `cookie`/`chrome.history` action with a `*`-bearing path cleans BOTH, not just one -- this is the single most important thing to verify given it's the reason this fix exists. `cleaners.json`'s own existing structural tests (rule-loading, no hardcoded drive letters, etc.) must keep passing unchanged. Each new/converted rule gets a scan+execute test through the real dispatcher (not just the underlying action module, which Phases B-D already tested in isolation) proving the JSON is wired correctly.
